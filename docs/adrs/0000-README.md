# Architecture Decision Records

1. [Web framework: FastAPI (v1) vs. Django for the rebuild](0001-fastapi-vs-django.md) — rebuild on Django + DRF instead of keeping v1's FastAPI app, since Django's built-in auth, ORM, admin, and storage give durable multi-tenant job state essentially for free.
2. [Task execution framework for the remediation pipeline](0002-task-execution-framework.md) — use Django's first-party `django.tasks` (`ImmediateBackend` locally, swappable to Cloud Tasks later via config) to run remediation out-of-band, avoiding Celery/RQ's always-on broker and worker requirement.
3. [Remediation pipeline: artifact-based step architecture](0003-pipeline-steps-and-branching.md) — the pipeline is a fixed sequence of six responsibility-based stages, each recording its outcome as an immutable `RemediationArtifact` row, with no partial success or resume: a failed job fails outright (see [ADR 0009](0009-no-retry-mechanism-yet.md) for current retry semantics — there aren't any yet). Now seven stages and two renamed steps — see [ADR 0010](0010-split-tag-construction-from-ocr.md).
4. [OCR/tagging engine: OpenDataLoader as a pinned dependency](0004-ocr-tagging-engine.md) — pin Java + OpenDataLoader (hybrid Docling mode) as a real, named dependency for the `ocr`/`finalize_tags` stage rather than hiding it behind a generic swappable OCR interface, since OpenDataLoader can't cleanly separate OCR from tagging anyway. Amended by [ADR 0010](0010-split-tag-construction-from-ocr.md): OpenDataLoader's hybrid+tagged-pdf combination turned out to be broken, so tag-tree construction moved to its own step and tool.
5. [Alt-text engine: Claude Vision](0005-alt-text-engine.md) — use Claude Vision for the `alt_text` stage for now, since v1 already validated it end-to-end, while flagging OpenDataLoader's built-in SmolVLM output as untested against the WCAG bar and worth a real future comparison.
6. [General mechanism for tracking engine/service comparisons](0006-engine-comparison-tracking.md) — add a permanent, reusable `EngineComparisonSample` table (gated by `RUN_ENGINE_COMPARISON_LOGGING`) for logging and manually comparing any two services' output on the same input, first used to compare SmolVLM against Claude Vision for alt-text.
7. [Java version: 21, not 25](0007-java-version.md) — use Java 21 (not the newer Java 25) for veraPDF and OpenDataLoader, since Java 25 has a live, unresolved JDK regression affecting the `ServiceLoader`/JPMS mechanism both tools' Apache PDFBox-based Java engines rely on.
8. [Storage layout keyed by document, not filename](0008-storage-layout.md) — key storage paths by `(service_account, content_hash)` rather than upload filename, so every attempt on a document groups together and multi-tenant isolation is preserved on disk, not just in the DB.
9. [No retry mechanism yet; resubmitting a failed document no longer auto-retries](0009-no-retry-mechanism-yet.md) — dedup and retry are different concerns; a `FAILED` document now stays reported as `FAILED` on resubmit instead of silently kicking off a new job. Retry mechanism is deferred for the future.
10. [Split tag construction into its own `build_tags` step](0010-split-tag-construction-from-ocr.md) — OpenDataLoader's hybrid mode silently drops OCR-recovered text from `tagged-pdf`/`pdf` output (confirmed bug, isolated at the raw Java CLI level); keep OpenDataLoader for OCR/layout via `format=json` (proven correct), and build the actual tagged PDF from that JSON via a new Apache PDFBox-based step instead. Also renames `finalize_tags`/`TaggingService` to `finalize_metadata`/`MetadataService`, since that step never touched tag structure, only document metadata.
